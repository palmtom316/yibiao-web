## 1. 冻结的产品决策

1. **交付 Docker Web 应用。** PVE 承载 Ubuntu/Debian VM，VM 内运行 Docker Compose；不把 Electron 装进容器，不走 noVNC。
2. **沿用本 Web fork。** 保留 Fastify、Prisma/PostgreSQL、React、JWT、首次改密、项目作用域、模块授权、SSE 和现有写标流水线。
3. **官方桌面只作算法来源。** 按固定提交移植提示词、算法、分批与检查点；不整仓 rebase，不在服务端引入 Electron。
4. **PostgreSQL 是唯一业务数据库。** 现有 OpenCode 兼容路径已依赖 `better-sqlite3`；这是已知例外，不得新增 SQLite 业务表。P0 不因清理此依赖而破坏兼容路径。
5. **证照与知识分域。** 证照、原件、持有人、有效期走资产/人员域；方案叙述、组织措施和可复述业绩文字走知识域；业绩档案连接它们。
6. **第一期是单公司、多人各自管理项目。** 现有项目权限为所有者及管理员可访问；不承诺普通用户同项目协同编辑、项目成员管理或多租户。
7. **第一期单 app 实例、单 Node 进程。** 当前任务锁、事件总线和配置缓存依赖进程内状态；不得直接使用 PM2 cluster 或 Compose 多副本扩容。
8. **人工确认决定商务响应。** 子串/标签搜索只产生候选；模型和关键词命中不能直接认定资格满足。
9. **交付可追溯。** 项目引用保存内容与文件版本，不能只保存源 ID；对外生成只使用允许引用且已确认的资料。
10. **先完成最小业务闭环。** 商务清单与附件包不等待 OpenXmlHelper、自动配图、ComfyUI 全部完成。

## 4. 目标架构与通用契约

### 4.1 容器与运行时

```text
PVE → Ubuntu/Debian VM → Docker Compose
                         ├─ nginx :443 → client 静态资源
                         │              /api 与 SSE → app
                         ├─ app：Fastify、Pi、LibreOffice（单进程）
                         ├─ migrate：一次性迁移/初始化，成功退出后 app 才启动
                         └─ postgres:16（不映射宿主端口）

持久化：pgdata；app 的 /data；独立备份目标
可选增强：OpenXmlHelper（P1-04）；本地图表渲染（P1-05）；ComfyUI 后置
```

- Node 使用 **22 LTS、最低 22.19.0**；P0-01 固定实际补丁版本。使用 Debian 系基础镜像，避免未经验证换成 Alpine。
- 客户端继续 npm + `package-lock.json`；服务端继续 pnpm 10 + `pnpm-lock.yaml`，固定包管理器版本，不在 P0 顺便改成单一 monorepo 工具链。
- 服务端沿用 `tsx src/index.ts` 启动方式。运行镜像必须带 tsx 和运行时所需的 `.cjs/.mjs`；迁移镜像带 Prisma CLI、schema、migrations、seed 及内置文档。不能假定 `tsc` 输出可直接裸 `node` 运行。
- Dockerfile 提供独立 nginx 静态目标与 app 目标；Compose 显式选择目标，避免构建出的 client 文件没有进入 nginx 镜像。
- 固定 `YIBIAO_DATA_DIR=/data`；DB 存相对路径，业务 API 返回文件 ID/授权地址，不把容器绝对路径交给浏览器。
- `VITE_SOURCE_REPOSITORY_URL` 是客户端**构建时**参数；仅设置 app 运行时环境变量不会改变已构建网页。

### 4.2 数据域与权限

| 数据域 | 访问规则 |
| --- | --- |
| 用户域 | 用户配置、个人模板与反馈遵循原权限；提示词等共享配置由管理员维护 |
| 项目域 | 项目所有者或管理员；接口、SSE、文件与任务都校验实际项目归属 |
| 公司共享域 | 公司单域，不按 userId 分区；`knowledge-base` 模块控制资料访问和维护 |

共享表可增加 `createdByUserId/updatedByUserId` 用于审计，这不等于把共享资料改成个人所有。第一期继续允许管理员和拥有 `knowledge-base` 的用户维护资料，不额外引入复杂 ACL。

资产候选查询、引用、快照下载和含资产附件的导出，必须同时验证项目权限及 `knowledge-base` 权限；基础技术标功能不因此新增模块门槛。长任务启动后仍由服务端解析和校验源 ID，不能信任客户端提交的路径或“已授权”标志。

### 4.3 密钥与处理出口

- 浏览器只提交新密钥，不接收已保存密钥；所有 GET/PUT 配置响应脱敏，并返回 `configured` 状态。空输入保留旧值，清除用显式操作，掩码不能被保存成密钥。
- P0 只使用部署方批准的内部模型/企业网关。服务端采用端点白名单，拒绝任意外部图片和未批准的远程图表服务；网关自身的外部转发由部署策略约束。
- P1-02 增加项目级 `allowExternalProcessing`，默认 false，只允许管理员改变；共享知识资料使用独立的管理员策略，默认 false，不能借用请求头中的某个项目开关。
- 外部模型、MinerU、公网生图及外部图表服务都使用同一授权判定：部署端点允许且该数据域允许。缺少数据域上下文时拒绝外发；重定向后的目标也需重新校验。
- 经校验的数据域上下文随任务传递到解析器、AI 服务和 Agent proxy；不能用修改全局配置来切换某个项目的授权。并发项目分别执行各自策略，重试时重新检查当前授权。
- 本地解析失败不能自动上传外部服务。外部服务失败可以回落本地，但必须记录原因与结果质量。
- Pi/工具运行不得绕过上述边界：控制实际工具读写根、符号链接、命令参数与环境变量。第一期不提供任意 bash；用受控文件工具/结构化命令替代，未适配的 Agent 路径明确降级。
- Agent 任务可用当前项目输入副本，不能读取其他项目、全量资料库或宿主配置；不向工具子进程继承数据库/JWT/模型密钥。禁止挂载 Docker socket。
- 日志、测试报告、浏览器错误和导出清单不得包含密钥。诊断文件按现有保留期限管理，不额外复制完整客户原文到通用日志。

### 4.4 文件与解析结果契约

P1-01 在现有 DTO 上**增量**补充以下语义，不删除原有 `markdown/parserLabel/chars/hash/fallbackToLocal`：

| 对象 | 必需语义 |
| --- | --- |
| 原件 | `sourceId`、原文件名、MIME、大小、SHA-256、相对存储路径、所属项目或共享文档 |
| 解析版本 | `parseVersion`、解析器/版本、状态、警告、`sourceHash`、Markdown hash/路径 |
| 图片清单 | `assetId`、SHA-256、MIME、大小、相对路径、可用时的页码/块位置 |
| 引用地址 | 稳定的文件 ID；浏览器预览走授权 API，导出由服务端解析同一 ID |

实现要求：

1. 原件先持久化，再启动解析；重试使用原件，不依赖请求临时目录。已有仅 Markdown 的记录标记 `sourceUnavailable`，需要原件的能力提示重新上传，不能伪造原件。
2. 图片先写临时产物目录，解析成功后原子发布清单；失败清理未提交产物，不覆盖旧成功版本。
3. 删除临时上传目录不得删除已发布图片。重复文件使用独立业务 ID；是否按 hash 去重不影响项目隔离。
4. 拒绝客户端绝对路径、`file:`、目录穿越与越界符号链接；解压 OCR 结果时限制路径、文件数、总解压大小。
5. 图片进入 Markdown、知识引用、正文与导出时可解析同一份资产；缺图必须显示警告，不能无声跳过。
6. 图片统一保留或转换为受支持格式；WebP 等导出限制明确处理。原件及中间产物设置大小、页数和超时上限。
7. 长解析返回任务 ID 并持久化进度。已有上传调用方同步适配，保留旧数据可读性；不把 MinerU 长轮询绑在一个浏览器请求中。

## 5. 公司资产、业绩与商务响应模型

### 5.1 资料分类

| 材料 | 权威存储 | 作用 |
| --- | --- | --- |
| 营业执照、资质、ISO、安全生产许可、软著、专利 | 公司库 `AssetItem.library='company'` | 结构化台账与原件 |
| 工具截图、采购证明、工具附件 | 工具库 `library='tool'` | 工具证明与附件 |
| 身份证、职称、注册证、社保、劳动合同 | `PersonnelProfile + PersonnelCertificate` | 持有人与一人多证 |
| 方案、组织措施、可复述业绩文字 | 知识文档/条目 | 目录、事实、正文引用 |
| 中标通知、合同、验收文件和项目叙述 | 原件进公司库，叙述进知识域，`PerformanceRecord` 聚合 | 可核对的类似业绩 |

“XX 医院弱电工程”应有一份业绩档案，关联合同/验收原件、叙述知识条目及项目经理。项目岗位保存在关联表，不写进证书备注。

### 5.2 台账最小补充

- 公司资质补 `category/certificateNo/qualificationLevel/holderName/issuer/validFrom`，复用 `expiryDate`；非证照资产这些字段可空。
- 人员证书补 `certificateNo/qualificationLevel/issuer/validFrom`，复用 `certName/certType/obtainedAt/expiryDate`，持有人继续由 profile 关联；取得日期不自动等于生效日期。
- 公司/人员证照新增 `validityKind=dated|permanent|unknown`；dated 必须有 expiryDate。存量有到期日归 dated，空值归 unknown，不自动归为永久有效；非证照工具附件不参与资格有效性判定。
- 时间比较以项目投标截止日期为核验基准，采用 Asia/Shanghai 的业务日期、到期日当日有效；未设置核验日期时结论保持待核验。
- 历史字段缺失允许录入和浏览，但候选结果标为“资料不足、待核验”。不得要求 AI 从文件名猜证号、等级或金额。
- 关键新增实体及台账维护有操作者、时间和版本号；历史记录的操作者可空，不伪造归属。并发更新校验版本，冲突返回 409，避免后保存覆盖前保存。

### 5.3 业绩档案

```text
PerformanceRecord
  id / title / ownerName / location
  contractAmount Decimal(20,2)?     金额单位：元；未知为 null
  currency                         默认 CNY
  contractSignedAt? / startedAt? / completedAt?
  durationText / roleText           文字补充，不代替结构化核验
  projectType / summary / notes / tags[]
  isPubliclyCitable                 默认 false，明确允许后才能对外引用
  version / archivedAt?
  createdByUserId / updatedByUserId / createdAt / updatedAt

PerformanceAsset(recordId, assetItemId)
PerformanceKnowledgeDocument(recordId, documentId)
PerformanceKnowledgeItem(recordId, itemId)
PerformanceTeamMember(recordId, profileId, role)
```

采用真实关联表与外键、组合唯一约束和反向查询索引，不把关系仅存为 JSON ID 数组。金额 API 以十进制字符串传输，不能依赖 JS 浮点比较资格门槛。

关联知识条目必须属于已关联知识文档；团队成员必须存在。引用前校验状态与版本；重新抽取知识导致条目变化时显式提示刷新关联。禁止引用的业绩及其受限叙述不能通过“直接选择关联知识条目”绕过对外引用限制。

### 5.4 引用版本与删除

**原计划“只存 ID 快照、导出时才拷贝”废弃。**

- 确认引用时生成项目级不可变 `ProjectReferenceSnapshot`：源类型/ID/版本、选定结构化字段、摘要/知识正文、确认人/时间、来源 hash、允许用途，以及文件清单。
- 文件在确认时复制至 `/data/<projectId>/workspace/references/<snapshotId>/`，校验 SHA-256；业务主记录与 manifest 全部成功才置 `ready`。跨 DB/文件系统不能假定单事务覆盖，使用 staging 状态和失败清理/重试。
- 项目导出读取 `ready` 快照。源修改、替换、归档或后续删除均不能改写已确认版本；需要新内容时显式“刷新引用”，产生新版本并保留历史。
- 快照的来源 ID 是溯源值，不能设置为随源删除级联删除快照的外键。找不到源时显示“来源已缺失”，已存快照仍可核对。
- 源实体默认归档。仍被业绩档案活动关联的源资料删除返回 409 并列出引用；先解除关联才可物理删除。知识重抽取也不得绕过关联保护。
- 删除人员级联清证书仅适用于允许物理删除的源记录，并清理对应源文件；不得清理项目内已复制的快照文件。
- 归档与撤销对外引用分开：归档不改变历史快照；撤销允许用途后阻止新的引用/生成及新的对外交付，历史产物不自动改写或删除，并保留撤销记录。
- 对含受限资料的历史快照，新导出要检查撤销记录。页面隐藏、源记录删除和模块权限变化都不能成为绕过此检查的路径。
- 撤销记录按源类型/ID 保留，生命周期独立于源实体；源被删除也不能删除撤销记录。混合了多个来源的叙述按最严格用途限制处理。

### 5.5 商务响应与技术标引用

至少定义三个项目域对象：

| 对象 | 关键字段/约束 |
| --- | --- |
| `BusinessRequirement` | 项目/标段、类别、要求原文、来源文件/hash、页码或块定位、门槛结构化值、核验日期、抽取版本、人工修订标记 |
| `BusinessMatch` | 要求 ID、候选资料 ID/版本、命中理由、已知满足项、不满足项、未知项、人工结论与确认人/时间 |
| `BusinessResponseRevision` | 不可变要求/结论副本、快照 ID 清单、版本/hash、状态、导出记录；关联不可跨项目 |

规则：

1. 先支持人工录入/粘贴，再加独立的商务要求抽取 runner；继续禁止技术分析 prompt 把商务资质混进技术目录。
2. 状态至少区分“候选/待核验/已确认满足/部分满足/缺失/不适用”。关键词命中只决定候选排序，只有人工确认能进入“已确认满足”；不适用也要理由。
3. 金额、资格等级、有效期、业绩时间范围、角色等条件逐项展示；任何关键未知项都禁止自动判为满足。第一期不计算最终投标得分。
4. 重新抽取产生新版本，不覆盖人工确认；来源 hash/核验日期变化使旧结论标记需复核。
5. 技术标只读取已确认快照；模型可改写许可的叙述，合同额、证号、人员名称等权威字段使用结构化渲染并做回查。生成不得改变已有人工章节。
6. 第一版 Word 是封面/响应清单，ZIP 包含该 Word、排序后的附件原件及 manifest。**不承诺把任意 PDF 原件转换成可编辑 Word 或自动合并成整套商务投标书。**
7. manifest 记录要求、文件名、来源快照和 hash；同名附件使用稳定序号避免覆盖。缺失/未 ready/已撤销附件阻止正式出包；可另导出带明显标记的缺项草稿。

- **依赖：** P2-01；测试部署以 P0 通过为前提。
- **落点：** 新 `routes/performance.ts`、`client/src/features/performance/`、菜单/权限映射；复用资产上传组件与人员组件。
- **契约：** `/api/performance-records` 下提供列表/详情/新增/更新/归档及显式关联维护；列表支持 q/page，更新带 version；接口均挂 `knowledge-base` 门禁。UI 不显示内部路径或数据库术语。
- **实施：** 上传必选资料类型，可关联或新建业绩；“业绩原件”写公司库并关联，不新建 `library='performance'` 文件柜。`performance` 仅用于实体/API/菜单标识。
- **验收：** 建人→多证→建业绩→挂原件/知识/项目经理完整完成；可以区分未许可引用与可引用；30 天到期列表覆盖公司/人员证，无权限者看不到附件；归档/删除符合第 5.4 节。
- **回退：** 隐藏新增业绩入口，保留记录与原有三库能力。

#### P2-03 遗留人员迁移与批量录入门禁

- **依赖：** P2-01、P2-02；批量扫描件录入需先通过 P1-02。
- **落点：** `asset-library` 写接口、迁移脚本、资料导入说明及迁移报告。
- **实施：** 后端拒绝向 `library='personnel'` 新增/更新，保留迁移期只读和受控迁移。脚本先 dry-run，列源 ID→profile/certificate ID、冲突、文件数与 hash；不凭同名自动合并人物。
- **执行：** 无法判断持有人的条目留待人工映射；迁移可重复运行不重复建人/证，复制并核对原件，验收前不删除旧文件。
- **无存量场景：** 提交零条待迁移的核查报告，仍完成旧写接口关闭和回归验证即可；不为填满迁移步骤制造历史数据。
- **验收：** 已迁移、冲突、待人工处理数量守恒；二次执行无新增；源/目标文件 hash 一致；旧只读入口能定位新记录。
- **回退：** 依映射报告撤回新增关联与记录，旧数据仍在；不自动“择机清掉”旧库。

### 6.4 P3：资料进入技术标与商务交付

#### P3-01 商务要求清单与独立抽取

- **依赖：** P1-01、P2-02。
- **落点：** 新 `business-bid/` store/routes/runner，现有 `BusinessBidPage`、任务类型与注册表。
- **实施：** 先打通人工要求清单，再独立抽取资质/业绩/人员要求；保存原文证据、源 hash、标段和核验日期。参考响应偏离表的溯源/人工修订机制，不复用其业务结果表。
- **验收：** 同一招标的技术目录未混入商务项；要求可定位原文；人工编辑后重新抽取不会覆盖；切换标段/更新原件需复核；任务关页继续且重试不重复写要求。
- **回退：** 关闭自动抽取，保留人工清单和历史版本。

#### P3-02 候选匹配、人工确认与不可变快照

- **依赖：** P3-01、P2-03。
- **落点：** 商务匹配服务、`ProjectReferenceSnapshot` / `BusinessResponseRevision`、文件复制与撤销用途记录。
- **实施：** 按第 5.5 节查询候选并展示逐条件证据；确认引用时检查当前版本/用途/权限，再复制字段、正文和文件。确定性核验负责数值/日期，模型只辅助解释。
- **验收：** 覆盖名称相似但等级不足、证书已过期、金额未知、截止日边界、业绩不可公开、源版本变化。不得自动把未知变满足；源文件替换/删除后旧快照 hash 不变；复制中断可恢复且未 ready 不可正式导出。
- **回退：** 停用新的自动推荐/确认，保留已确认版本；不能退回只存源 ID。

#### P3-03 业绩/团队注入技术标

- **依赖：** P3-02。
- **落点：** 目录候选、全局事实与正文 runner；章节引用 UI。
- **实施：** 显式选业绩/团队及目标章节，读取快照中的许可叙述；证号、金额等结构化字段可核对，记录章节→快照来源。已有知识引用链路继续保留。
- **验收：** 测试样本中的金额、证号、人名均与快照一致；不可引用资料不进入模型请求；模型增加未经支持事实时阻止确认并提示；重复生成不覆盖人工锁定章节。
- **回退：** 关闭自动注入，已生成正文和来源关系保留可人工编辑。

#### P3-04 商务 Word/ZIP 出包与最小闭环验收

- **依赖：** P3-02；完整业务闭环验收另要求 P3-03。
- **落点：** `business-bid`、`export/`、下载 API、商务页与菜单文案。
- **实施：** 以已确认响应版本生成清单 Word + 原件 ZIP + manifest，处理顺序/中文同名文件/缺失/撤销；服务端流式出包或临时产物下载，避免大量原件一次装入内存。长任务提供 jobId 和重试。
- **菜单：** 主入口改为“商务响应”，替换计算器占位；不新增竞品测算。导出草稿与正式包状态明确区分。
- **验收：** 一份脱敏招标从要求→候选→人工确认→快照→清单/原件包可复现；ZIP 文件数量、排序和 SHA-256 与 manifest 一致；两个用户不能下载彼此项目包；重试不重复创建版本。
- **回退：** 停止新出包，既有响应版本/快照/产物保留；不回写源资料。

内置自由对话编辑、按用户多模型分流、ComfyUI、图片知识库、复杂只读/资料员 ACL、自动评分、实时协同和多实例工作队列均不作为本期任务。需要时另写方案及验收，不顺带塞进上述任务。

## 8. PVE 资源与运维约定

| 用途 | vCPU | RAM | 数据盘起点 | 说明 |
| --- | --- | --- | --- | --- |
| 开发预览 | 2 | 4 GB | 40 GB | 只验证低并发，不代表生产容量 |
| 约 5 人起步 | 4 | 8 GB | 80 GB+ | 解析/导出受服务端队列约束 |
| 约 10 人起步 | 8 | 16 GB | 160 GB+ | 必须实测等待时间、峰值内存与磁盘增长 |

这些数值是试配起点，不是已测性能承诺。记录样本页数/大小、队列长度、成功率、耗时、峰值 RSS、数据增长；在不串任务/不 OOM 的前提下再调并发。

- 推理服务独立于业务 VM；应用访问受控 API，不把 Ollama/vLLM GPU 推理塞进 app。
- PostgreSQL、app、可选渲染服务不映射外部端口。只开放 443；证书有效性与续期归属在部署记录中写明。
- 备份目标必须是独立磁盘/远端存储；同 VM 的另一个目录不等于独立备份。PVE vzdump 作为补充，不替代逻辑恢复演练。
- 起步备份目标：每日一份，保留最近 7 份日备份及 4 份周备份；升级前另做一份。目标 RPO ≤ 24 小时、RTO ≤ 2 小时，P0-05 用实际数据演练后记录是否达到；达不到就调整方案，不伪报达标。
- 加密/限权保存配置与备份；不把真实 .env、源文件、证件或 dump 放进仓库/镜像。备份记录含 backupId、校验和与恢复步骤。
- 监测磁盘剩余、任务失败、队列积压、备份失败和证书到期；临时文件/日志设置保留期。保留策略不能清理仍被引用的原件与快照。
- 健康检查不依赖公网模型成功；外部服务降级单独报告，不能引发 app 不停重启。
- AGPL 页面指向当前运行修改版的可访问源码，并记录版本/构建提交；只链接官方桌面或不同版本仓库不满足本计划验收。

## 9. 验收矩阵与剩余风险

### 9.1 固定验收样本

使用脱敏或合成样本并附人工预期，不提交真实客户资料。至少准备：带图片/表格 DOCX、文本 PDF、扫描 PDF、旧 Office、多文件/多标段招标、空/损坏/超限文件；公司与人员过期/未知证书；公开/不可公开业绩；缺原件和同名附件。

模型服务用可重复的 mock 覆盖错误分支，同时保留真实受控端点验收；不能用一次“模型说成功”代替产物核验。新增长任务按任务类型列出“重启后续跑/暂停/中断待重试”的预期。

| 验收组 | 必须观测到的结果 | 对应任务 |
| --- | --- | --- |
| A01 构建/初始化 | 干净构建；空库可用；已有库 baseline 正确；重复启动不重置密码/正文 | P0-01/03/04 |
| A02 密钥与隔离 | 所有配置响应无测试密钥；API/SSE/文件/导出/工具均无跨项目访问 | P0-02 |
| A03 全流程与恢复 | 首次改密；分析到 Word；关页继续；重启状态明确；恢复后的文件 hash 与原备份一致 | P0-04/05 |
| A04 解析与出口 | 图片导出完整；扫描件无 OCR 时明确失败；外发被策略阻止；失败不毁原件 | P1-01/02 |
| A05 检索/模板/配图 | 分页边界正确；Linux helper 真实产物有效；离线图表可导出；降级可见 | P1-03/04/05 |
| A06 台账与迁移 | 关系完整、金额精度/日期规则正确；同名人物不误合并；迁移数量与 hash 守恒 | P2 |
| A07 商务真实性 | 关键词命中不自动满足；未知/过期/不可公开被正确标记；人工修改不被重抽覆盖 | P3-01/02 |
| A08 快照与技术标 | 源变更不改快照；引用撤销阻止新交付；权威字段无无依据变更 | P3-02/03 |
| A09 出包 | Word/ZIP/manifest 一致；无重复/同名覆盖；缺件不静默出正式包；权限正确 | P3-04 |
| A10 并发与容量 | 至少两个项目同时操作，事件/产物不串；超限排队可见；停止进程有界完成 | P0-04/05，P1/P3 新增长任务 |

### 9.2 风险处理规则

- OpenXmlHelper 构建或模板能力不可用：维持普通目录路径，记录未完成项；不阻塞资料与商务闭环。
- MinerU 无法处理扫描件：保留原件并标“需 OCR/人工处理”；若扫描件是主要材料，阻止批量录入交付，不能计作解析成功。
- 外部模型不可用：资料维护与人工清单继续可用；生成任务记录失败/重试，不反复自动扣费。
- 磁盘满、复制中断、迁移失败：不得置产物 ready 或发布半成品；停止对应操作并保留可恢复状态。
- 当前任务状态和缓存依赖单进程：容量不足先限流与测量；横向扩容需另立任务所有权/租约/共享事件方案。
- 上游继续变化：只更新已登记的对照项，不因官方新功能自动扩大本期范围。

## 10. 建议执行顺序与发布门禁

### 10.1 推荐顺序

1. **P0-01**：冻结环境、建立验证入口和状态记录。
2. **P0-02 + P0-03**：关闭已确认的密钥/资源缺口，建立数据库迁移与安全 seed。
3. **P0-04 → P0-05**：Docker 构建、运行、带数据升级/恢复演练；完成基础部署交付。
4. **P1-01 + P2-01 → P2-02 → P2-03**：先持久化原件，同时建可靠台账与业绩；schema 迁移由一个集成顺序管理。
5. **P1-02（扫描件用户优先）与 P1-03**：改善批量录入和检索；不等它们全部完成才准备商务清单。
6. **P3-01 → P3-02 → P3-03/P3-04**：尽早验证真实一份招标的完整闭环。
7. **P1-04、P1-05、P1-06**：独立推进并逐项发布质量增强，正确性修复可按影响前移。

可以分别准备独立任务，但同一文件/同一迁移链不能同时无序修改。P0 尚未验收时只在开发/测试环境准备后续任务，不把新业务堆入待稳定的 PVE 部署。

### 10.2 每次发布的门禁

- 必需前置任务和适用 A01～A10 项有证据；未通过的功能明确禁用，不能用菜单已出现代替完成。
- 从当前基线与带数据上一版本各走一遍适用验证；新功能不破坏登录、项目、技术标、已有方案扩写及资料访问。
- 涉及 schema/文件布局时说明兼容窗口、升级顺序和回退方式；不能只写“回滚 git commit”。
- 记录源 commit、镜像 digest、schema migration、数据目录格式版本与启用功能；交付源码入口可访问。
- 功能后置与失败降级必须在状态表中可见；基础部署通过不等于本计划全部完成。

## 11. AI 实施与交接规则

### 11.1 开工流程

1. 阅读本文、`CONTRIBUTING.md` 和目标目录的适用约束，检查 git status；保留用户现有修改，不能 reset/覆盖未归属当前任务的内容。
2. 读取 `docs/implementation/STATUS.md`；首次由 P0-01 创建。每行至少有任务 ID、TODO/IN_PROGRESS/BLOCKED/DONE、负责人、前置、实现 commit/文件、验证报告、遗留问题、回退说明。
3. 校验实际源码与第 2 节差异；后续提交不是重新从旧 HEAD 开始的理由。已完成任务复用证据，不重复实现。
4. 选择一个前置已满足的任务，先给出涉及文件和验收项，再实施到服务端、客户端、数据与部署的完整路径。涉及 API 的新增 DTO/错误码同步到调用方。
5. P0-01 创建 `docs/implementation/BASELINE.md`；每项完成写 `docs/implementation/<任务ID>-verification.md`。来源移植另写 `UPSTREAM-PORTS.md`。

### 11.2 必须建立的验证命令

P0-01 负责补齐下面缺失的脚本；**在补齐前，不得把这些命令写成已经执行通过。** 每个代码任务跑适用检查，阶段出口跑完整检查。

客户端，在 `client/`：

```bash
npm ci
npm run typecheck
npm run build
npm test
```

服务端，在 `server/`：

```bash
pnpm install --frozen-lockfile
pnpm exec prisma generate
pnpm run typecheck
pnpm run build
pnpm test
```

P0-04 后容器验证，在仓库根目录且使用独立测试环境配置：

```bash
docker compose config --quiet
docker compose build
docker compose up -d
docker compose ps
```

测试脚本使用临时数据库和临时数据目录；显式校验测试目标，不连接现网。容器启动命令本身不代表验收通过，仍需执行第 9 节的操作及断言。依赖缓存/网络/真实模型缺失时报告准确阻塞与已完成部分，不伪造实测结果。

### 11.3 完成定义与交接内容

标记 DONE 前同时满足：实现完整、适用检查通过、失败/权限路径有验证、文档与配置同步、回退可执行。只有 mock 验证而任务要求真实 Linux/数据库/OCR 实测时，保持未完成。

每次交接必须写明：

- 完成的任务 ID、改动文件/commit、实际行为和对应验收项。
- 测试命令、结果、环境、报告位置；未执行项和原因单独列出。
- 数据迁移、文件布局和兼容性影响；部署变量及是否需要重建前端。
- 剩余风险、被关闭的功能、回退步骤、下一项任务及其前置。
- 尚未获得运行环境时保留可审查产物与具体执行步骤，不把环境缺失解释为工作已完成。
