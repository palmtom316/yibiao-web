# PVE 单人系统测试前全仓代码审核与优化意见

日期：2026-09-13（Asia/Shanghai）

审核基线：`main` / `5a926ae64fc5983a3219bd3f9aa10cc113af144a`

场景：PVE 内 Ubuntu/Debian 虚拟机、Docker Compose 单实例、一人执行系统测试；不包含在 VM 内部署大模型或 MinerU 推理服务。

## 1. 审核意见

**可以先在隔离内网部署并验证启动、登录和基础资料维护；完整单人系统测试前，建议先修复本报告的 P1 项。当前版本不宜直接作为真实投标项目的连续工作环境。**

已有的 JWT 首次改密、每请求权限复查、项目归属、配置密钥脱敏、原件版本化、引用快照、迁移及同批备份值得保留。主要缺口出现在部分链路没有使用这些公共机制：Agent 自检绕开处理出口；查重绕开受限解析；工作副本发布未与数据库状态保持一致；偏离表确认/导出没有重新验证来源；后台任务在错误落库再次失败时可能使进程退出。

本次只增加审核文件和复现证据，不修改业务实现、数据库结构或历史验收状态。此前 [9 月 9 日审核](CODE-REVIEW-2026-09-09.md)、[9 月 10 日修订](CODE-REVIEW-2026-09-09-FIXES.md)、[9 月 11 日部署说明](PVE-PRE-DEPLOY-2026-09-11.md) 是历史材料，不能替代本次对当前源码的核查。原 `snapshotHistory` 空 `OR` 的误报保持撤回。

配套执行清单：[PVE 单人系统测试清单](PVE-SOLO-TEST-2026-09-13.md)。

### 级别与证据口径

- **P1**：影响处理边界、数据一致性或服务稳定性；完整系统测试前优先修复。允许先做不经过相关链路的基础冒烟。
- **P2**：会影响特定功能或运维，有明确规避方法；纳入测试缺陷清单。
- **优化**：改善维护、性能和运维，不建议为此大规模重构后再开始测试。
- “复现”指对当前真实函数/路由运行合成输入；数据库替身和网络拦截会明确标注。它不等同于真实模型、完整浏览器或 PVE 验收。

## 4. 详细审核意见

### R01 · P1 · Agent 自检未经过统一处理出口

定位：[piSelfCheck.ts](../../server/src/agent/pi/piSelfCheck.ts#L454) 第 454 行；`piRuntimeService.ts:1848`；`routes/agent.ts:53`。

`/agent/self-check` 虽然创建了 `administration` 作用域，普通/流式/工具调用三个探针仍直接使用全局 `fetch`，携带平台 `Authorization`。它们不调用 `processingFetch`，也不检查 `YIBIAO_INTERNAL_ENDPOINTS` / `YIBIAO_EXTERNAL_ENDPOINTS`；原生 fetch 的重定向行为也与统一出口不同。

这里能确认的是**固定自检提示和 API Key 绕过端点策略**，不将其夸大为已经发送了客户招标原文。合成复现会在空白名单和拒绝授权器下拦截所有 fetch，检查请求次数及是否携带认证头，不发送真实网络请求。

建议：统一经过 `processingFetch`；给管理探测明确的批准规则，或绑定已验证的项目作用域，不能仅因为操作者是管理员就绕过部署白名单。将自检、模型列表、生图测试、普通生成一起做出口矩阵测试。

验收：空白名单 `sends=0`；已批准内部端点可用；外部端点须满足明确授权；重定向拒绝且不出现真实密钥。

测试期间规避：真实密钥配置前修复；未修复时不运行 Agent 自检。

### R06 · P1 · 导入失败可能破坏旧工作副本的一致性

定位：[technical-plan/store.ts](../../server/src/technical-plan/store.ts#L1692) 第 1692–1718 行；已有方案导入第 1751–1759 行。

`importTenderDocument` 先删旧 `tender-files`、写新分源 Markdown、替换 `tender.md` / `tender-original.md`，然后才执行数据库事务。若数据库连接、事务或提交失败，接口最终失败，但文件已经变更；原来的 metadata/hash/下游正文仍可能保留。`importOriginalPlanDocument` 有相同顺序问题。

独立 `DocumentSource` 原件和解析版本仍保留，不能描述成“所有原件丢失”；问题是**当前工作副本与数据库指向失配**。合成复现对真实 store 注入事务失败，检查旧分源文件和当前 Markdown 的变化。

建议：导入结果写入独立、不可变的版本目录，完整校验后在一个数据库事务中切换当前版本及清理下游状态；旧版本在切换成功前保留。将文件发布、DB 切换、重试和孤立 staging 清理定义为同一状态机。导入/清空/切标段还应与正在运行的生成任务互斥。

验收：在写文件前、写文件后、事务提交前分别注入失败；旧有效项目的文件、hash 和正文始终一致；重试成功后只切换一次。

测试期间规避：使用一次性项目测试替换导入；真实内容替换前做同批备份；失败后核对原件列表、来源 hash 和当前正文，不仅看通知文案。

### R07 · P1 · 错误处理中的再次失败可终止进程

定位：[tasks/service.ts](../../server/src/tasks/service.ts#L551) 第 551–579 行。

后台 Promise 链在 runner 失败后调用 `await updateTask(..., true)`。该错误状态写库若也失败，前面的 `.catch` 自身就会拒绝；后续只有成功 `.then`，没有末端拒绝处理，内存任务清理也会被跳过。项目默认 Node 22 行为会把未处理拒绝升级为进程退出。

建议：明确捕获“任务失败”和“终态持久化失败”，在 `finally` 清理活动任务/队列范围，末端捕获只记录脱敏上下文；不能把落库失败包装成成功。需要退出时采用可观测、受控的退出及启动恢复。

验收：runner 失败叠加状态库不可用时，不能出现未处理拒绝；DB 恢复后状态可辨认、可重试，其他项目请求不被这一任务意外终止。

测试期间规避：故障注入先使用临时项目；服务恢复后刷新页面并检查任务和文件一致性。

### R08 · P1 · 查重没有复用有界解析链路

定位：[duplicate-analysis.ts](../../server/src/tasks/runners/duplicate-analysis.ts#L222) 第 222–230、257–262、504–505 行；对照 `document/sources.ts:50–72`、`document/parse-worker.mjs:14–20`。

查重直接在 app 进程执行 `convertPathToMarkdown`，同时启动元数据读取；图片转为内嵌 base64。它没有进入 `parseQueue`，没有使用 768 MiB V8 堆/180 秒超时的解析子进程，也没有先执行新解析入口的 PDF 页数和 Office 解压检查。不同项目的查重任务可以和正常解析竞争同一进程资源。

合成复现只用两个很小的 Markdown：占满唯一解析槽位时，查重仍完成正文提取。这证明队列被绕过，**不声称已做大文件压测或复现 OOM**。

建议：将查重的正文、元数据及图片提取纳入可取消、限时、限内存的 worker，保留查重需要的元数据字段；采用资源 ID 或独立图片文件，减少 base64 膨胀。服务端校验整个查重文件集合，而不只校验单次上传批次。

验收：解析槽位占满时查重进入队列；超过页数/解压/图片限制可控失败；失败不会阻塞健康检查；两个项目并行时总解析并发仍符合配置。

测试期间规避：先用小型、来源明确的样本，避免同时运行查重和其他文档解析；修复后再做边界和负载测试。

### R05 · P1 · 偏离表的来源过期状态能被重新确认覆盖

定位：[response-deviation/store.ts](../../server/src/response-deviation/store.ts#L189) 第 189–208 行；`routes/response-deviation.ts:45–53,83,105–108`；`response-deviation/export.ts:443–444`。

来源变化检查只在 `/availability` 读取时触发。`confirmWorkspace` 不验证当前原文/标段，也不拒绝 `stale`，直接写回 `confirmed`。正式导出只检查已存状态和表格内容，不重新取当前来源。旧页面在另一标签页更换原文后，或对过期结果再次提交确认，都可能拿到旧要求的 Word。

建议：在确认、导出两处都与当前招标 hash、标段和提取器版本比较；来源无效则返回 409 并保持过期状态。将“确认哪个版本”作为请求与持久化契约；更新原文时同步使旧表失效。

验收：生成并确认 A → 更换原文/标段为 B → 不调用 availability，直接确认或导出旧版本，均返回 409；重新生成并人工复核 B 后才允许导出。商务响应已有 `checkRevision`，可参考其校验原则。

测试期间规避：更换原文/标段后重新生成偏离表；导出人工比对原文编号和 hash，不使用旧标签页的确认状态。

### R02 · P2 · 外部模型测试的实际作用域与部署说明不同

定位：[routes/ai.ts](../../server/src/routes/ai.ts#L30) 第 30–47、74–96 行；`security/processing-authorizer.ts:20–22`。

只有 `/chat` 和 `/request-json` 调用 `createRequireProject`。`/list-models` 和 `/test-image-model` 即使带 `X-Project-Id`，也只有 SSE 项目戳，没有 `req.projectId`，因而绑定 `administration`；该作用域的 `allowExternal` 恒为 false。

**更正 9 月 11 日说明第 4.1 节：管理员 + 已选项目 + 项目外部开关 + external 白名单，仍不足以让“拉取模型列表”通过。** 文本聊天测试和列表测试的行为不同。

合成复现还观察到相同管理作用域被检查 3 次：`ai/service.ts:775–778` 将出口拒绝也标记为可重试，应保留权限拒绝的不可重试语义，避免无效等待。

建议：需要项目上下文的管理探测先验证并绑定该项目，或设计独立、明确授权的管理探测能力；同步修订帮助文案。不要通过把公网模型填进 internal 名单来替代作用域修复。

验收：管理员在已批准项目拉取外部模型列表成功；无项目、未批准项目、普通用户分别按契约拒绝；同时覆盖生图测试。

规避：手填模型名，通过已批准项目验证实际文本生成；单独记录列表/生图测试的已知限制。

### R03 · P2 · SSE 在正常 EOF 后不会恢复

定位：[client SSE](../../client/src/shared/api/sse.ts#L85) 第 85–136 行；`server/src/routes/events.ts:4`。

服务关停通过 `stream.end()` 正常结束连接。客户端没有 `onclose`，而 `fetch-event-source` 在正常 EOF 后结束 Promise；只在 `onerror` 处理重连不够。`started` 仍为 true，后续 `start()` 也不会重新打开连接。后台任务 API 设计又主要依赖 SSE 更新。

另一个同处问题：无活跃项目也启动 SSE，服务端返回 400，客户端持续重试；首次配置时会产生无效请求。

建议：为非主动关闭的 EOF 明确触发带退避的重连与快照刷新；用连接实例标识避免旧回调修改新连接状态；无项目不连接，400/404 等不可恢复错误不无限重试。

验收：备份停启、正常 SIGTERM、网络中断、切项目各做一次；同一页面无需刷新即恢复进度和权威快照；首次无项目登录不循环报错。

规避：服务重启或备份结束后手动刷新页面。

### R04 · P2 · 唯一管理员可以自降权

定位：[users.ts](../../server/src/routes/users.ts#L95) 第 95–97、116 行；`UserManagementPage.tsx:283`；`seedInitialAdmin.ts:50`。

停用和删除已经禁止操作自己，但修改角色未作同类检查，也未保证至少一个 active 管理员。唯一管理员可以从界面把自己改成 user，随后管理请求 403。seed 在用户表非空时跳过，不能作为恢复办法。

建议：服务端事务内保证至少一个可登录管理员，并防并发降权/停用；UI 给出一致限制；提供需要服务器管理权限的恢复流程。

验收：唯一管理员自降权被拒绝；存在另一个 active 管理员时按产品契约处理；并发操作不能把可用管理员降为零。

规避：测试期不修改唯一管理员角色；角色权限测试使用另外的测试账号。

### R09 · P2 · 活跃项目偏好没有读回

定位：[config/store.ts](../../server/src/config/store.ts#L80) 第 80–90、186–194 行；`routes/projects.ts:91–104`；`client/src/app/ProjectContext.tsx:45–63`。

激活项目写 `UserConfig.data.activeProjectId`，但 `buildMerged` 只取个人偏好白名单，这个字段被丢弃。前端找不到提示值便选列表首个项目。此外，首次解析只等项目列表，不等 config 请求完成。

### R10 · P2 · AI 诊断项目编号筛选会构造无效 Prisma 查询

定位：[ai-diagnostics/routes.ts](../../server/src/ai-diagnostics/routes.ts#L24) 第 24 行；`prisma/schema.prisma` 的 `Project.projectCode`。

筛选构造 `where: { code: ... }`，模型实际字段为 `projectCode`。`(app as any).prisma` 避开了类型检查，正常输入项目编号也会走无效查询。这是源码与 schema 对照确认，不能用现有类型检查通过来排除。

建议：使用 `projectCode`，给 Fastify decoration 和 service 查询参数准确类型；对编号过滤做真实 Prisma 路由测试。

验收：已有、无匹配、空项目编号均返回正确列表/空列表，不返回 500。

### R11 · P2 · 部分“取消”只改变任务显示状态

定位：[jobs/service.ts](../../server/src/jobs/service.ts#L65) 第 65–67 行；`routes/knowledge-base.ts:47–53`、`knowledge-base/pipeline.ts:162`、`routes/technical-plan.ts:23–26`。

`JobService.cancel` 触发 AbortController 并写 cancelled，但知识准备 runner 未接收/传递 signal，`prepareDocument` 调用 `parseSource` 时也未传信号；准备完成后还会调用 `kickoffExtraction`。部分模板 runner 同样忽略信号。因此 cancelled 不能代表计算或后续外部调用已经停止。

建议：所有长作业传递 signal；排队、开始工作、发布、启动后续任务之前检查取消；无法立刻停止的阶段显示“取消中”，最终结果不能只由前端按钮决定。

验收：在排队、解析中、解析结束但抽取未开始三个时点取消；不得再启动知识模型请求，不发布半成品，原件和旧成功版本保留。此项为调用链静态发现，需补目标环境时序测试。

## 7. PVE 部署意见

1. **建议起步 4 vCPU / 8 GiB RAM / 80 GiB SSD**，另准备独立备份位置。README 的 2 核/4 GiB 是轻量功能验证估计；当前 Compose 的 app 上限 4 GiB、PostgreSQL 2 GiB、nginx 256 MiB，加上 OS、构建和临时内存，不适合按“4 GiB 肯定够”承诺。限额不是内存预留；最终按实测调整。
2. 选择 **Ubuntu 24.04 LTS 或 Debian 12 及以上兼容版本**。备份脚本使用 `hashlib.file_digest`，需要 **Python ≥ 3.11**；仅安装 Ubuntu 22.04 默认 Python 3.10 会在备份 hash 阶段失败，应先检查版本或改兼容实现。Node/npm/pnpm 使用仓库固定版本。
3. 初测使用基础 `app` 目标，明确记录 Word 模板 helper / 本地图表未启用；需要这些功能时单独启用 `app-enhanced` 并验收。增强 helper 固定 `linux-x64`，目标 VM 应确认 x86_64；增强镜像构建及 C# 运行不能由本次宿主检查代替。
4. 只开放受限来源的 HTTPS 443；数据库/app 不映射宿主端口；使用有效 TLS 和实际 `YIBIAO_PUBLIC_ORIGIN`。Compose `config --quiet` 只验证配置，`up --wait` 也不能代替浏览器 TLS 检查；nginx 当前没有独立健康检查。
5. 全新卷走 migrate → seed → app；不在测试数据上随手执行 `db push` / `migrate reset`。记录源码 commit、实际镜像 ID、迁移列表和启用功能。首次改密完成后验证旧密码失效。
6. 端点配置先走批准的内部网关或 external 白名单；项目与共享资料分别授权。MinerU 创建、上传、轮询、下载地址都需要覆盖。先修 R01/R02，不扩大白名单掩盖功能故障。
7. **必须做一次目标 VM 的同批备份与空环境恢复**，核对数据库记录、全部文件 hash、图片和导出。PVE 快照/vzdump 是补充；本机旧日志和同一业务盘另一目录不能证明目标备份可用。备份保留 7 日/4 周等策略在脚本中尚未自动实现。
8. PM2 仅作为备选；其 nginx 示例仍为 HTTP、`client_max_body_size 100m`，与 Compose 的 HTTPS/201m 不同。不能直接把该示例当成等价生产配置。

放行单人系统测试的依据应是：P1 修复及回归、目标 VM 启动/TLS/改密通过、批准模型与解析服务可用、一次备份恢复成功、关键业务闭环和已知限制有记录。它不自动等于多人或生产放行。
