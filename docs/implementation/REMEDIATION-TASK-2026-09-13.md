## 四、R01–R12 的完整修订要求

### R01：Agent 自检绕过处理出口（P1）

入口：`server/src/agent/pi/piSelfCheck.ts`、`server/src/agent/piRuntimeService.ts`、`server/src/routes/agent.ts`、`server/src/security/processing.ts`。

让普通、流式和工具调用三个自检探针使用统一受控网络出口。管理探测必须有明确授权规则；需要项目作用域时先验证项目访问权，再传递作用域。每次实际发送和重试都保持同一授权语义，禁止跟随未批准重定向。

验收：空白名单时网络发送为 0；批准的内部端点可按管理权限调用；外部端点必须满足所选数据域策略；账号或权限失效后拒绝；拒绝响应和诊断不包含密钥。用真实路由与被拦截的网络发送验证，不能只测 URL 辅助函数。

### R02：模型列表和生图测试作用域错误（P2）

入口：`server/src/routes/ai.ts`、`server/src/security/processing-authorizer.ts`、`server/src/ai/service.ts`、设置页。

为模型列表和生图测试建立正确的、已验证的处理作用域，不能只写 SSE 项目戳。与 R01 使用一致的管理探测规则。保留普通用户的管理接口限制；权限拒绝、无效配置等不可恢复错误应立即返回，不反复重试。

验收：管理员在正确授权项目调用批准外部端点成功；无项目、无权限项目、未授权外部处理和普通用户场景按契约拒绝；拒绝时发送为 0 且不重复重试；内部端点行为仍符合约定；文本聊天、模型列表、生图测试一起回归。同步修正部署文档和页面提示。

### R03：SSE 正常 EOF 后不重连（P2）

入口：`client/src/shared/api/sse.ts`、`client/src/app/ProjectContext.tsx`、`server/src/routes/events.ts`。

处理服务正常结束事件流的情形，加入受控退避重连，并在重连后读取当前项目的权威快照。区分主动退出、切项目、权限失效和可恢复断线；旧连接回调不能改写新连接状态。没有活跃项目时不创建无效连接。

验收：正常 EOF、网络中断、app 重启后同一页面自动恢复；切项目和退出后旧连接停止；401/403、无效或已删除项目不无限重试；每个页面只有预期的有效连接；旧项目快照不会覆盖新项目。补浏览器或等效真实流集成验证。

### R04：唯一管理员可自降权（P2）

入口：`server/src/routes/users.ts`、`server/src/db/seedInitialAdmin.ts`、用户管理页面。

在数据库事务内保证至少保留一个可用管理员，覆盖改角色、停用和删除等相关路径。必须处理两个管理员并发操作的情况，不能只在前端禁用按钮。保留首次安装强制改密流程，不用重复 seed 重置账号作为修复手段。

验收：唯一管理员自降权被拒绝；其他角色管理按明确契约工作；并发操作不能使可用管理员数量变为 0；前端能解释拒绝原因；为历史异常状态提供仅服务器管理员可执行的恢复说明，不增加公开恢复接口。

### R05：过期偏离表仍能确认和导出（P1）

入口：`server/src/response-deviation/store.ts`、`server/src/routes/response-deviation.ts`、`server/src/response-deviation/export.ts`。

在确认和正式导出时重新核对当前招标来源 hash、标段及提取版本，确认对象必须是明确版本。来源已经失效时保持过期状态并返回 409；不能依赖前端先调用 availability。原文替换、标段变化以及并发确认/导出的校验规则必须一致。

验收：确认 A 后替换为 B，不调用 availability 直接确认或导出 A，均拒绝；显式 stale 不能被直接改回 confirmed；并发更换来源时不会导出错误版本；重新生成并人工复核 B 后可正常导出，已有人工填写内容按原有保护规则处理。

### R06：导入时文件与数据库失配（P1）

入口：`server/src/technical-plan/store.ts`、`server/src/document/imports.ts`、`server/src/document/sources.ts`。

重构招标文件和已有方案导入的发布顺序。新结果写入独立版本或 staging，完整校验后由数据库切换当前引用；切换完成前旧成功版本保持有效。定义事务失败、文件操作失败、崩溃后的恢复和孤立 staging 清理。保持现有原件和解析版本机制。

导入、清空、切标段与正在运行的生成任务应有一致的互斥或版本检查，避免后台任务覆盖新来源。新实现需要兼容旧路径和旧项目；如需迁移，增加新 migration 或明确兼容读取措施。

验收：在写文件前、写文件后、数据库提交前后分别注入故障，当前项目的文件、hash、元数据和下游状态保持一致；服务重启后能确定实际生效版本；重试幂等；两次并发导入不能混合发布；原件和旧成功版本保留。

### R07：错误落库失败造成未处理拒绝（P1）

入口：`server/src/tasks/service.ts`，并检查后台作业中同类 Promise 链。

区分 runner 失败和错误状态持久化失败，确保所有异步链有终端错误处理。在 finally 清理活动任务、控制器和队列作用域，记录脱敏诊断；持久化失败不能标成成功。恢复策略应明确，避免内存锁永久残留或数据库状态看似完成。

验收：runner 失败叠加数据库不可用时无未处理拒绝；其他请求不会被意外终止；活动任务和队列能释放；数据库恢复后任务可识别、可恢复或可重试。需要子进程测试证明默认 Node 22 行为安全，不能仅靠测试框架全局捕获异常让测试通过。

### R08：查重绕过有界解析（P1）

入口：`server/src/tasks/runners/duplicate-analysis.ts`、`server/src/tasks/utils/duplicateAnalysisHelpers.ts`、文档解析 worker 和资源队列。

把查重的正文、元数据和图片提取移到有界、可取消的 worker，与其他文档解析共享正确的并发预算。保留查重依赖的真实元数据、文字和图片比对功能，避免嵌套入队造成死锁。服务端校验整个分析文件集合及每份文件。

设置并验证堆内存、输出字节、解压字节、图片像素/数量、页数和耗时限制。V8 堆上限不等于总 RSS 上限，原生图片库和子进程内存也应纳入观测。减少正文内嵌 base64 带来的内存放大。

验收：唯一解析槽位被占用时查重排队；两个项目同时处理仍不突破并发预算；超限、损坏文件、超时和取消可控失败；健康检查仍可响应；原件保留；小型已知样本的元数据、正文和图片查重结果没有功能退化。

## 六、测试、部署与验收

工具链默认保持 Node 22.23.2、npm 10.9.3、pnpm 10.17.1、PostgreSQL 16。备份脚本需要 Python ≥3.11，或提交并验证明确的兼容实现。依赖整改若涉及工具链不兼容，记录方案并同步核对所有版本声明，不能只在一台开发机上临时升级后宣称兼容。

服务端在 `server/` 执行：

```bash
pnpm install --frozen-lockfile
pnpm exec prisma generate
pnpm run typecheck
pnpm run build
pnpm test
pnpm run test:integration
pnpm audit --prod --json
```

前端在 `client/` 执行：

```bash
npm ci
npm run typecheck
npm run build
npm test
npm audit --omit=dev --json
npm audit --json
```

基线只需完整运行一次；修订过程中先运行与改动相关的用例及必要类型检查。全部修改完成后，在最终提交内容上跑一轮完整检查。验证后又改动相关实现时，补跑受影响检查。审计返回非零时区分“成功查询后有告警”和“网络/工具失败”。
