## 3. 部署与首次启动

先完成 `.env`、证书和备份路径配置；从仓库根目录操作：

```bash
docker version
docker compose version
python3 --version
git rev-parse HEAD
docker compose config --quiet
docker compose build
docker compose up -d --wait
docker compose ps --all
docker compose exec -T app node -e "fetch('http://127.0.0.1:3000/health/ready').then(async r=>{console.log(r.status,await r.text());process.exit(r.ok?0:1)}).catch(()=>process.exit(1))"
```

- 根 `.env` 中设置随机、URL-safe 的数据库密码及随机 JWT_SECRET，替换示例值；`chmod 600 .env`。
- `BUILD_COMMIT` 填实际提交；前端源码入口指向当前运行修改版；这些前端变量改变后要重建 nginx。
- PostgreSQL healthy、migrate **Exited (0)**、app healthy、nginx running 是预期状态；不要要求一次性 migrate 一直 running。
- 从测试终端访问 HTTPS，证书可信、主机名匹配；确认仅应用 443 入口开放，app 和数据库无宿主端口。
- 首次 `admin/admin` 登录只允许改密；改密后退出，再验证旧密码被拒绝、新密码可登录。
- 不重复运行生产 `db push`，不使用 `docker compose down -v` 清测试环境中的保留数据。

如果要测试增强能力，按部署指南使用独立 override 将 `app.build.target` 设为 `app-enhanced`，再重建/重建容器；记录与基础镜像不同的镜像 ID。第一轮未启用的功能记为“未测”，不能记通过。

## 4. 配置顺序

1. 建立一个一次性项目，确认页面当前项目和请求的 `X-Project-Id` 一致。
2. 在部署配置中登记获批的模型/解析端点；改变环境变量后重新创建 app 容器使其生效。
3. 管理员设置模型服务商、Base URL、模型名及密钥。使用未列出的网关时选“自定义”。
4. 外部模型处理开启项目授权；知识库含共享资料时另开共享授权。白名单和数据域许可是两项独立条件。
5. R02 未修复时，手填模型名，用实际文本生成确认连通性；模型列表失败不代表凭据一定错误。R01 未修复时不运行 Agent 自检。
6. MinerU 验证创建、预签名上传、轮询、下载四类地址；记录解析 provider 和回落警告。不能把回落本地成功当成 MinerU 成功。
7. 先验证文字文件，再验证扫描 PDF。无 OCR 时扫描文件应明确提示需 OCR/人工处理，不能以空正文继续生成。

## 5. 功能用例

按顺序执行，每条记录实际结果、问题编号和证据路径。未修复的已知问题记录“失败/受限”，不要跳过后标整体通过。

| ID | 操作 | 期望结果/判据 |
| --- | --- | --- |
| S01 | 空数据卷启动、完成改密、再启动一次 | 初始化幂等；不重置密码；内置文档不被覆盖 |
| S02 | 管理员创建 A/B 两项目；切到 A 后刷新 | 当前项目正确恢复；核对 R09；两项目的正文、任务和文件互不混用 |
| S03 | 一人用不同浏览器会话登录两个普通测试账号 | 未授权模块被拒绝；A 用户不能通过项目 ID 读取 B 项目；停用后旧会话失效 |
| S04 | 唯一管理员尝试自降权 | 应拒绝并保留管理入口；R04 未修复时仅在可重建测试环境验证 |
| S05 | 导入中文名/空格文件名的文字 PDF、DOCX、Markdown | 文件名正确；原件可下载；hash、解析版本、文字/图片/表格可核对 |
| S06 | 导入扫描 PDF，分别测试 OCR 可用/不可用 | 可用时 OCR 结果明确；不可用时明确失败或质量警告；原件保留 |
| S07 | 同一原件重解析；再模拟解析失败 | 成功版本递增；旧成功版本及原件保持可读；失败不冒充新成功版本 |
| S08 | 在有已生成正文的项目替换原文；注入 DB 提交失败 | R06 修复后旧工作副本和 DB 一致；失败可安全重试 |
| S09 | 完成招标解析、单/多标段、目录、全局事实、正文 | 阶段状态正确；选择标段真实限制输入；关键要求有原文依据 |
| S10 | 人工修改正文后尝试重新生成、调整目录、插图 | 已锁定人工正文不被静默覆盖；冲突有明确提示 |
| S11 | 正文暂停、继续；切离页面、关闭再打开 | 任务语义明确；已生成部分保留；不重复启动同一任务 |
| S12 | 使用已有方案扩写 | 原方案上传、来源、目录、扩写结果、人工内容保留均可核对 |
| S13 | 知识库上传、搜索、分页、空词、超尾页、引用 | 只返回可用且获准的内容；共享处理策略生效；选中参考资料不会漏记共享域 |
| S14 | 公司资质、人员多证、业绩金额/日期/关联/归档 | 金额无浮点误差；到期日当天有效；未知期限不当永久有效；冲突版本拒绝；引用关系有保护 |
| S15 | 商务要求抽取、候选、人工说明、确认、版本、Word/ZIP | 候选不直接算满足；未核验只能草稿；正式包原件齐全且 hash 可核对 |
| S16 | 确认引用后修改/归档源资料，再撤销引用许可 | 已确认快照保持原值；撤销后新导出拒绝；不能静默改掉历史事实 |
| S17 | 生成偏离表并确认，另一标签页更换招标文件/标段，再导出 | R05 修复后拒绝旧版本；重新生成并复核后才可导出 |
| S18 | 两份小型文件查重，再与普通解析同时运行 | R08 修复后共用受限资源；失败可定位；不能以空解析结果给“无重复” |
| S19 | 废标项抽取与检查 | 风险与原文证据对应；失败/遗漏明确；不把 AI 输出直接等同于最终合规判断 |
| S20 | Word 导出，打开 Word/WPS 核查 | 中文、层级编号、表格、图片、页码、模板正确；缺图警告可见；无服务端本机路径 |
| S21 | 增强模板扫描、字段确认、本地 Mermaid/HTML/配图 | 未启用时明确降级；启用后不访问未批准外网；签字/盖章仍手工；图源及错误可恢复 |
| S22 | 使用文档编辑、提示词修改、FAQ、设置保存 | 管理权限正确；保存后读回一致；重启/seed 保留用户编辑 |
| S23 | 人为制造一次模型错误，按项目编号查诊断 | R10 修复后可筛选；trace 可关联任务；响应/日志无密钥 |

## 6. 故障与容量用例

在可恢复的测试环境做；先完成备份。不要对承载其他业务的数据库或 Docker 服务执行故障命令。

| ID | 场景 | 期望结果 |
| --- | --- | --- |
| F01 | 普通 SIGTERM / `docker compose restart app` | 正文保留可继续；其他任务明确中断；SSE 无需刷新即恢复（R03） |
| F02 | 关闭浏览器、断开客户端网络、重新连接 | 后台任务不中止；重连取权威快照；不重复扣费/生成 |
| F03 | 任务失败叠加测试数据库暂时不可用 | R07 修复后无未处理拒绝；错误及恢复状态可识别 |
| F04 | 模型超时、401、429、5xx、格式错误 | 有限重试；上游 401 不导致用户被登出；错误可诊断；不丢原件 |
| F05 | 知识准备/模板作业排队和运行时取消 | R11 修复后信号传到具体工作；不启动后续外部请求；可区分取消中/已取消 |
| F06 | 损坏文件、空文件、超文件/批次大小、超页数 | 在明确阶段拒绝；健康检查和其他请求仍可用 |
| F07 | app 重建、VM 重启 | 使用原卷；项目、配置、图片、引用和任务恢复符合约定 |
| F08 | 备份、空环境恢复、再导出 | DB 和文件同一 backupId；全部 hash 通过；账户、文档和导出可用 |

从小样本逐步增加页数和图片量；R08 修复前不将高压查重结果作为容量结论。至少记录一个完整工作时段的 CPU、RSS、OOM/restart、磁盘增长、队列等待和失败率。

```bash
docker stats --no-stream
docker compose ps --all
df -h
```

容量判据不预先伪造具体吞吐：记录每份样本的大小/页数、上传时间、排队时间、解析时间、生成/导出时间与峰值资源。以自己的真实使用规模决定是否需要更多内存和磁盘。

## 7. 同批备份与恢复演练

先核实 Python ≥ 3.11、磁盘空间、独立备份目标与恢复 override；备份在维护窗口运行：

```bash
python3 deploy/backup/backup.py --help
python3 deploy/backup/restore.py --help
```

实际调用参数按 [部署指南](../DEPLOYMENT.md) 填入自己的受保护 `.env` 和目录。恢复必须使用独立 Compose project 和空卷，不能指向当前业务卷。

记录：backupId、是否保存离线镜像、写入服务实际停止时间、恢复耗时、hash 核对结果、恢复后登录/原件下载/Word 重导出结果。`restore.py` 成功后 app 仍停止，需核对兼容镜像再启动。

RPO ≤ 24 小时、RTO ≤ 2 小时是目标，只有在目标 VM 演练后才能写实际值。失败目录没有完整 manifest 就不能作为有效备份。调度、保留 7 日/4 周、加密和异地保管需要部署方落实。

## 8. 测试记录模板与结束条件

每个缺陷使用以下记录项：

| 字段 | 填写要求 |
| --- | --- |
| 基线 | 应用 commit、镜像 ID、测试用例 ID |
| 输入 | 合成/脱敏样本 ID 和 hash；账号角色、项目编号 |
| 操作 | 能复现的最短步骤；是否重启/取消/切换来源 |
| 期望/实际 | 状态码、任务状态、输出差异；区别配置错误与程序缺陷 |
| 证据 | 脱敏日志、trace/job ID、截图或导出文件位置；不记录 token/密钥 |
| 处理 | 优先级、修复提交、回归结果、剩余限制 |

单人阶段结束条件：P1 已修复并回归；核心业务闭环通过；错误、暂停、重启和取消行为明确；目标环境恢复成功；未启用/未通过能力有清单；没有来源/项目串用、旧内容被静默覆盖或密钥出现在浏览器响应的情况。

缺少真实模型、MinerU 或合适样本时，相应条目记录“未测/缺外部条件”；基础冒烟通过不能替代这些条目。
