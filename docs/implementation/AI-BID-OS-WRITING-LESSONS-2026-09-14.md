# 对照 `ai_bid_os`：可借鉴的编写质量机制

编制：2026-09-14。对照仓库：`/home/palmtom/projects/ai_bid_os`（本机目录名是下划线）。本仓库基线：`yibiao-web` `main` @ `b433ac0`。配套：投标实务审查 [BID-EXPERT-REVIEW-2026-09-14](BID-EXPERT-REVIEW-2026-09-14.md)。

**目的**：只回答“为提高**技术标编写质量**，yibiao-web 该学什么、不该整段搬什么”。不评价两边的产品形态优劣，也不把 `ai_bid_os` 的国网施工默认蓝图当成易标的默认大纲。

---

## 0. 两边不是同一类产品

| | yibiao-web | ai_bid_os |
| --- | --- | --- |
| 形态 | 多租户 Web，项目隔离，JWT，浏览器工作台 | 本地 CLI + Obsidian vault，技能流水线 |
| 对象 | 通用招标（货物/服务/工程），商务+技术+审核工具 | 以国网施工/配电运维为深的技术长文工厂 |
| 写作单元 | 目录叶节点，默认约 3000 字/节，模型扩写 | 先 31 个 leaf，再拆约 250 个 writing unit，先契约后写作 |
| 招标进入写作的形态 | markdown + 18 项自由文本/JSON 槽 | 14 类结构化事实，每条必须有 **source block + 逐字 quote** |
| 质量门 | 一致性/原方案覆盖（模型审模型）；商务导出有总闸，技术 Word 无 | 确定性门：评分闭合、去套话、表格、证据引用、digest 绑定的语义/段落审查 |
| 知识复用 | 知识库整篇引用 | 方法卡 + 领域包（可执行工序，不是整本旧标） |

结论先说：`ai_bid_os` 在**“写之前把评分点变成可检查契约”**上明显更强；yibiao-web 在**原件纪律、商务确认快照、人机界面、多租户安全**上更强。提高编写质量，应把前者的契约思想接到后者的流水线上，而不是移植 Python/vault 架构。

易标其实已经有半步：`outline-v2` 按技术评分项规划目录，`proposalStructureCoverage` 检查招标“技术方案章节清单”是否被目录覆盖。缺的是把这一层**推进到正文、证据和导出门禁**。

## 1. 对方写作链路（精简）

```
parse（块级原文）
  → structure（14 类，失败封闭：无 quote/签名不一致则整批作废）
  → draft（评分映射、偏离、骨架）
  → longform --prepare（矩阵、事实、证据、writing unit 契约、评估策略、专家量表）
  → 人工确认 brief / 企业证据
  → 按 unit 写作（context pack 只带确认过的方法/事实/证据）
  → 确定性质量门 + 语义/段落审查（绑定正文 digest）
  → 出章
```

`--prepare` **不写正文**。这是质量关键：模型和人先对齐“这一节必须证明什么”，再允许生成。

---

## 2. 对编写质量真正起作用的机制（按借鉴价值）

### 2.1 响应矩阵先于写作（应作为易标第一借鉴）

`scripts/technical_longform_writer/response_matrix.py` 从结构化招标事实生成 `technical_response_matrix.json`：

- `requirement_id`、`quote`（原文）、`requirement`（条款）
- `target_section_ids` / `target_node_ids`（写到哪）
- `must_cover`（必须出现的要点）
- `needs_project_facts` / `needs_company_evidence`
- `recommended_method_card_ids`
- 评分点另从 `score_mapping.final.json`（已校验）或 `.initial.json`（种子）并入，并标注 `mapping_confidence`

这正是昨份投标审查里的「条款 → 章节 → 证据」。易标缺的不是“再写一遍长文”，而是**目录生成之后、正文之前的这一张表，且未确认不得开写**。

易标落点：扩展现有 `proposalStructureCoverage` + `outline-v2` 的 `score-directory-plan`，做成可编辑、可确认的项目对象（不要只做目录覆盖率统计）。

### 2.2 招标事实必须可定位，否则失败封闭

`tender-structurer` 抽 14 类（工期、质量、安全、资格、业绩、评分、废标、技术要求…）。每条必须带 source block 与 exact quote；批次 JSON 必须回传 `input_signature`，对不上整批作废。摘要由已校验事实**确定性**汇总，禁止模型编一段“项目概况”当事实。

易标 18 项招标分析是提示词切片，成功即写入 `bidAnalysisTasks[].content`，随后进入全局事实和正文。商务模块已经用 `rawText` 必须 `indexOf` 得着——技术侧应对齐这一条，而不是再发明一套。

### 2.3 写作单元契约，而不是“一节三千字”

`--prepare` 把 leaf 拆成 writing unit，每张契约包含：专家问题、论证维度、项目对象、风险、方法、证据、交付物、目标条款 ID、禁止跑题的主题边界。

默认 3000 字 + 800 字增量，是在奖励套话。unit 契约把生成目标从“写长”改成“回答这个问题并覆盖 must_cover”。

易标不必上 250 个文件。Web 上一个叶节点下挂 3～8 个**可折叠的写作任务**（结论 / 方法 / 风险 / 证据 / 记录）就够，和对方的六维闭合一致。

### 2.4 评分闭合门（确定性，可作导出闸）

`score_closure.py` 要求每个评分点在目标章节里同时出现六维信号：

`response_conclusion` · `project_object` · `method` · `risk` · `evidence` · `deliverable`

覆盖率默认阈值 0.85；目标章节无正文为 `missing`，不足为 `weak`。这是词表匹配，能被“堆关键词”钻空子，但比“模型说自己写得好”可审计。

易标应作为**正式 Word 导出的硬门**，与商务 ZIP 的 pending/unknown 总闸对称。不要把它宣传成“预测得分”。

### 2.5 专家量表是写作体检，不是中标预测

`templates/technical_writer/expert_rubric.yaml`：招标响应度、评分闭合深度、项目适配、措施可执行、风险控制、证据支撑等，每维有 1/3/5 级描述和正负信号（负信号包括“原则上、根据需要、高度重视、切实有效”）。

易标可做成正文生成后的**检查报告**（红/黄项 + 定位到章节），不要做评分引擎。昨份审查已明确：不要自动评分/中标预测。

### 2.6 方法卡 + 领域包，替代整篇知识库灌入

对方把旧标蒸馏成方法卡（工序、责任、记录、风险），领域包按业主/设施关键词打分后注入差异化对象和表。写作 context 只带**选中的卡**，不带整本旧方案。

易标知识库目前更像整篇引用，扩写时容易把旧项目名和旧招标条款带进新标。应在知识库上加一层“方法卡”（可先用人工标注，不必先做蒸馏大模型）。

### 2.7 企业证据只注入已确认项

`--apply-input-review` 之后，只有 `confirmed` 的 `company_evidence_pack` 进入 leaf context。证据在正文里以 `company:` 引用，并可追溯。

易标商务快照 + `yibiao-reference` 锁已经更严。技术正文应默认只注入这些已确认快照，**不要**把未确认的 18 项分析当事实。

### 2.8 去套话是确定性扫描，不是再让模型润色

`bid_anti_ai_tone.py` 统计“确保 / 有效 / 全面 / 切实 / 严格落实 / 形成闭环 / 提高效率 / 保障质量”等空话密度。对方注释里写明：还要用真实标书校准阈值。

易标一致性修复目前是模型再写一遍，容易越修越空。应先跑词表扫描，再决定要不要模型修补。

### 2.9 审查绑定正文 digest

语义审查、段落审查的 JSON 必须带 `reviewed_artifact_digest`；正文一改，旧审查作废。这避免“审过了但后来又扩写了三千字”。

易标任务状态机已有 progress/log，缺的是“审查对象哈希”。导出前若正文 hash ≠ 审查 hash，只能出草稿。

### 2.10 行业蓝图 vs 每次从零生成目录

对方用 `templates/blueprints/sgcc_power_construction_bid_v1` 等把评分点映射到稳定章节。易标 `outline-v2` 每次对当前招标现场规划，适应性更好，稳定性更差。

可借鉴的是**可选蓝图**：用户选“施工组织 / 运维服务 / 信息化实施”等模板，作为目录约束，而不是唯一大纲。不要把国网施工蓝图做成默认。

### 2.11 配图是带 schema 的交付物

图表有 catalog、planner、renderer、review，和 unit 绑定。易标已有 illustration 队列和 Mermaid/HTML。下一步应让图挂在响应矩阵行上，并检查导出后是否还有“规划了但正文没有图号”的节。

## 3. 明确不要整段搬的

1. **Obsidian / 文件系统项目布局** — 易标是多租户 DB + 对象存储，契约应进 Prisma，不要进用户磁盘树。  
2. **把 90 个 Python 模块当产品** — 借鉴对象是矩阵/闭合/方法卡，不是再做一个 CLI。  
3. **国网施工默认 31 章** — 会把货物/服务类标写成施工组织设计。  
4. **词表闭合当唯一质量标准** — 必须配人工确认和原文定位，否则会“关键词堆满、条款没答”。  
5. **自动打综合分 4.2** — 与易标“不引入评分引擎”的产品约束冲突。  
6. **扩写轮次和字数军备** — 对方质量来自契约，不是来自更长。

## 4. 建议移植到易标的形状（按编写质量收益）

对应流水线节点，而不是新开一条平行产品。

| 次序 | 借鉴对象 | 接到易标哪里 | 验收（编写质量） |
| --- | --- | --- | --- |
| 1 | 响应矩阵 | `outline-v2` 成功之后、`content-generation` 之前；UI 一张表，确认门禁 | 未确认矩阵时正文任务拒绝启动 |
| 2 | quote + 失败封闭 | `bid-analysis` 每项增加 `sourceLocator`/`quote`；进全局事实前必须人工确认或标不适用 | 无定位的项不能出现在 facts 注入列表 |
| 3 | 叶节点下的写作任务 | `content-generation` 按矩阵行生成 3～8 个任务；默认目标改为覆盖 `must_cover`，废除 3000/800 字硬指标 | 抽样章节能指出“本段在答哪条” |
| 4 | 评分闭合门 | 正式 Word 导出前跑六维扫描；weak/missing → 仅草稿 | 与商务缺项水印同一产品语言 |
| 5 | 已确认证据才注入 | 正文 context 只带 `confirmedReferenceFacts` + 已确认分析项 | 未确认证照/业绩不得进技术正文 |
| 6 | 去套话扫描 | 生成后、模型一致性修复前 | “高度重视/切实有效”超阈值标黄 |
| 7 | 方法卡 | 知识库文档增加 `method-card` 类型，章节计划只引用 ID | 扩写不再整篇灌入旧标 |
| 8 | digest 绑定审查 | 偏离表/废标/闭合报告写入 `artifactHash` | 正文再生成后旧审查失效 |
| 9 | 可选蓝图 | 模板库增加“技术标骨架”，用户选用 | 不替代当前招标目录生成 |
| 10 | 图绑定矩阵 | `contentIllustrationPlan` 增加 `requirement_id` | 有评分点无图时警告 |

第 1、2、4、5 项与昨份投标审查的「五件实事」重合，应视为同一批，不要做两套需求。

## 5. 易标已有、应保留并对齐的

不要在借鉴时冲掉：

- 商务：原文定位、`humanEdited`、快照复制、正式/草稿分流（这是 `ai_bid_os` 企业证据包还没做到的产品完成度）。  
- 原件版本、staging 发布、取消不覆盖成功结果。  
- `outline-v2` 的“技术评分项 → 目录分支”主线（对方用蓝图写死映射；易标现场规划更适合多行业）。  
- 偏离表 / 查重 / 废标作为独立工具——应收进出厂检查单，而不是删除。

`ai_bid_os` 的 structurer 14 类，可用来**校正**易标 18 槽的串类问题（须知 / 评标 / 采购需求 / 合同不要写进同一 markdown 槽），不必改成 14 这个数字。

## 6. 风险与范围控制

- 对方长文模块体量很大，全盘对标会把易标写成第二套国网工厂，并破坏 Web 交互。  
- 词表门禁有行业偏置（“交底记录、停电窗口、低压台区”）。移植时阈值和词表必须按易标行业可配置，默认用中性词（响应、措施、风险、验收、记录、证据）。  
- 没有真实招标对照集之前，矩阵和闭合门先对内、先警告，再视误报率改成硬拒绝。这与 STATUS 中真实 MinerU/模型仍 BLOCKED 一致。

---

## 7. 结论

`ai_bid_os` 对易标编写质量的价值，集中在一句话：

> **先把招标条款和评分点编译成可检查的写作契约，再允许模型动笔；写完用同一张契约做确定性闭合，而不是用字数和二次润色证明质量。**

易标若只从对方仓库吸收四样：响应矩阵确认门、分析项原文定位、叶节点写作任务（取代 3000 字扩写）、导出前评分闭合 + 去套话扫描——技术标就会从“能写长”转向“能指出这段在答哪一条”。方法卡、蓝图、digest 审查可以第二批再做。

不吸收：vault 架构、国网默认大纲、综合评分、把知识库整篇继续灌进提示词。
