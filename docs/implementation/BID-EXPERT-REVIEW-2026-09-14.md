# 投标实务专家审查：关键编制路径与改进建议

编制：2026-09-14。视角：工程/货物/服务类公开招标、竞争性磋商的投标文件编制人（技术标主笔 + 商务资格组卷），不是软件安全审计。代码基线：`main` @ `b433ac0`。配套产品说明见 [FEATURES](../FEATURES.md)，工程验收状态见 [STATUS](STATUS.md)。

**本文件不构成“可投标交付”或“可生产发布”结论。** 真实招标样本、真实模型/MinerU 端点尚未按 EXTERNAL-ACCEPTANCE 验收；下列评价针对**当前实现路径是否符合投标编制的工作方式与失败模式**。

---

## 0. 一句话总评

工程上，这套系统已经把“原件可追溯、确认才固化、失败不覆盖成功结果”做成了可辩护的骨架；投标实务上，它仍是**辅助起草台**，还不是**对照招标文件出厂的编制系统**。

商务路径（资格/证照/业绩 → 人工确认 → 不可变快照 → 带水印的正式/草稿分流）最接近投标组卷纪律。技术标路径（18 项抽取 → 目录 → 全局事实 → 按节约 3000 字扩写 → 一致性修补）仍是“先写长文再修补”，容易产出看起来完整、对照评分点却对不齐的套话。招标解析的最大实务风险不是“读不出字”，而是**读错标段、把评分表当技术规格、漏废标项**——这三件事会让后面所有写作建立在错误输入上。

当前适合：内网单人/小组，用合成或已熟悉的招标文件做**辅助起草、组卷和复核清单**。  
当前不适合：把系统输出直接当正式投标文件提交；暗标；联合体/分包；电子标 CA 签章封装；报价/控制价；未人工复核的资格响应。

## 1. 投标编制真正在做什么（对照坐标系）

正式投标文件通常拆成三本，失败原因不同：

| 分册 | 评委/招标人看什么 | 典型废标/失分 | 系统应对的正确姿势 |
| --- | --- | --- | --- |
| 资格/商务 | 证照是否在有效期内、业绩是否对口、原件是否可核 | 缺一项、过期一天、复印件当原件、联合体漏协议 | **未知 ≠ 满足**；确认时复制原件；来源变化必须复核 |
| 技术 | 是否按采购需求/评分点逐条响应 | 漏条款、答非所问、套话凑字、暗标露名 | **先建响应矩阵，再按格写作**；禁止无依据扩写 |
| 价格 | 是否按清单报价、算术是否正确 | 漏项、单价矛盾、未响应控制价 | 本产品明确不做报价引擎（正确）；不要用“投标计算器”占位误导 |

系统已覆盖：招标导入与解析、技术标流水线、商务要求抽取与确认、偏离表、查重、废标项、Word/ZIP 导出。  
系统未覆盖且必须在文档中保持诚实：报价、电子标封装、暗标去标识、联合体协议、签章/装订版式按招标模板强制套用。

## 2. 路径一：招标文件解析

### 2.1 当前方法

1. 上传走 `persistSource`：原件落盘、SHA-256、状态 `staging → ready`，上限 100 MiB，格式白名单。  
2. 解析走 `parseSource`：独立 staging 目录 + 有界 `parse-worker`（768 MB / 180 s / 12 MiB 输出缓冲）；配置了 MinerU 则先 OCR，失败且本地有字则回落并写警告。  
3. 校验通过后才把 `content.md` + `manifest.json` + 图片资源发布为当前解析版本；旧成功版本保留。  
4. 技术方案导入改为 staging 发布后再切当前引用（R06）。  
5. 多标段：正则只做“是否疑似多标段”的快检；真正列表由 LLM 分段抽取 + 合并去重。选定标段后用行号范围切出工作副本。  
6. 招标分析 runner 对选定正文并发抽取约 18 项（项目概述、技术评分、项目信息、甲方、交货服务、采购清单、响应文件要求、代理、关键节点、保证金、资格审查、符合性、开标、评标、商务评分、废标、合同授予、合同终止）。概述先跑以预热 prompt cache，其余并行。

### 2.2 评价（投标视角）

**值得保留的纪律**

- 原件与解析版本分离，失败/取消不覆盖成功结果——这是后续所有“对原文负责”的前提。  
- 解析进队列和子进程，避免大 PDF 把主进程打崩；扫描件走 OCR、文字件可本地解析，方向正确。  
- 标段切分用行号范围而不是再生成一份“改写过的招标”，减少二次失真。  
- 18 项里把**资格审查、符合性、废标、评分办法、交货验收**单列，说明产品知道这些不是“技术正文”的一部分。

**会在真实招标里翻车的点**

1. **表格才是招标文件的法律文本。** 资格条件、采购清单、评分表、偏离表模板几乎都在表里。本地解析有表格缝合测试，但合并单元格、双栏 PDF、扫描表、跨页表仍是行业第一杀手。MinerU 回落本地文字时只加一句警告，后续抽取仍会把残表当成全文——投标人看到的是“系统抽到了”，评委看到的是漏项。  
2. **标段切错 = 整本写错。** 正则快检“不生成最终列表”是对的，但 LLM 分段合并后只要漏一个标段或把“第 X 包”并进“第 Y 包”，后面目录和正文全部污染。目前没有“标段清单必须人工勾选确认才能进入分析/写作”的硬门禁（商务要求倒是有 `humanEdited`）。  
3. **18 项是提示词切片，不是按招标目录建模。** 真实文件的结构是“投标人须知 / 评标办法 / 采购需求 / 合同条款 / 附件格式”。系统按固定 18 槽去填，容易：  
   - 把合同违约条款写进技术要求；  
   - 把评分表（含商务分）写进技术评分；  
   - 把“无效投标”和“废标”混在一项（法律后果不同）。  
4. **抽取结果没有“对照原文高亮”的强制复核。** 商务抽取要求 `rawText` 必须能在 markdown 里 `indexOf` 定位，这是正确的；招标 18 项写入 `bidAnalysisTasks[].content` 后，直接作为全局事实和正文的输入，错误会放大。  
5. **真实 MinerU/复杂招标样本未验收**（STATUS 仍 BLOCKED）。没有这份证据，不能对扫描件、CAD 附图、印章页作质量承诺。

### 2.3 改进建议

| 优先级 | 建议 | 理由 |
| --- | --- | --- |
| P0 实务 | 标段列表增加**人工确认门禁**：未确认不得启动招标分析、目录、正文、商务抽取 | 写错标段无法用后期编辑挽救 |
| P0 实务 | 招标分析每项展示“原文定位/未定位”；未定位项标 `unknown`，不得进入全局事实 | 与商务 `rawText` 门禁对齐 |
| P1 | 解析产物增加**表格对象**（不只 markdown 管道符）：保留表头、行列、合并信息，供资格表和偏离表使用 | 资格和评分几乎全是表 |
| P1 | 18 项改为“招标目录映射 + 槽位”，至少拆开：投标人须知、评标办法、采购需求、合同条款、格式附件 | 减少串类 |
| P1 | MinerU 回落必须**阻断**依赖 OCR 的下游（扫描件禁止“本地有几个字就算成功”） | 假成功比失败更危险 |
| P2 | 用 3～5 份脱敏真实招标（货物/服务/工程、单标段/多标段、扫描+文字）做抽取对照集，按项统计漏抽/错抽 | 没有对照集就无法迭代提示词 |

## 3. 路径二：商务标——公司资料抽取与编排

### 3.1 当前方法

1. `POST /business-bid/extract`：对招标 markdown 做一次 JSON 抽取，`category ∈ {asset, performance, certificate, other}`，`rawText` 必须能在原文中逐字定位，否则 422 不落库。  
2. 重抽只归档 `humanEdited=false` 的自动项，人工改过的要求保留。  
3. 候选检索按类别在公司资产 / 人员证书 / 业绩中 `take 50` 名称/证号/标签匹配，**不是语义匹配**。  
4. `evaluateCandidate` 逐项给出 `met / failed / unknown`：引用许可、原件份数、证照在投标截止日是否有效、等级、最低合同额（币种不同直接 failed，不折算）、岗位、时间窗。未人工复核的要求额外挂 `humanReview=unknown`。  
5. 确认：`humanEdited` 未完成不得 `confirmed`；确认时对源记录 `SELECT … FOR SHARE`，把字段、叙述、原件**复制**进项目快照（含图片资产另拷），允许用途含 `technical-facts`。  
6. 已确认引用插入技术正文时用 `<!-- yibiao-reference:id -->` 锁住权威字段；改锁内文字会 409。  
7. 正式 ZIP/Word 导出前复核：来源 hash、标段、核验日期、要求版本、快照仍可用；缺项只能导出带“【缺项草稿·不可用于正式投标】”水印的草稿。

### 3.2 评价

这是四条路径里**最像投标组卷**的一条，也是最应该作为产品标杆向技术标推广的一条。

**做对了的投标纪律**

- 未知不自动算满足；币种不同不折算。  
- 确认复制原件，库里以后改证照/撤许可不影响已确认项目版本。  
- 招标换了、标段换了、截止日期换了，清单会 `needsReview`。  
- 正式件与缺项草稿分流，避免把“待核验”装进正本。

**仍会在开标现场出问题的点**

1. **资格条件是逻辑组合，不是四分类标签。** 真实表述是“具备建筑工程施工总承包一级 **且** 安全生产许可证在有效期内 **且** 近五年至少两项类似业绩，联合体牵头人须满足全部，成员可满足部分”。当前抽取不建模 AND/OR、联合体角色、分包范围、注册资本、社保人数、特定项目经理证书。人可以手工改 `rawText` 和 thresholds，但自动抽取帮不上忙，候选也匹配不准。  
2. **候选检索太弱。** `take 50` + 名称包含，遇到“类似业绩：医院弱电智能化”时，库里叫“某市人民医院信息化建设项目”的记录排不进来。投标商务组的实际工作是“按门槛筛库”，不是“按文件名搜库”。  
3. **`unknown` 在人工勾选后仍可确认。** 这在流程上合理（人可以凭纸质原件确认），但系统没有强制上传对应页或填写“核验说明”。出了过期证，责任完全在操作者，系统给不出“当时依据哪一页”。  
4. **人员是一人多证模型，但商务响应常见的是“项目经理/技术负责人/安全员”岗位包。** 有 `requiredRole` 门槛，没有“本项目拟派团队”编制和证书交叉校验（注册证专业是否对口、社保是否在本单位）。  
5. **自动抽取质量未用真实招标验收**（P3-01 BLOCKED）。在验收前，应默认“人工录入要求 + 系统只做候选与组卷”。

### 3.3 改进建议

| 优先级 | 建议 | 理由 |
| --- | --- | --- |
| P0 实务 | 抽取结果默认全部 `pending`，界面以原文高亮为主，门槛字段需人点“已核对” | 与现有 `humanEdited` 一致，强化默认姿态 |
| P1 | 资格条件建模：`allOf/anyOf`、联合体角色、时间窗、金额、证照包 | 否则只能当备忘录 |
| P1 | 候选改为门槛过滤（有效期、等级、金额、项目类型、岗位）+ 关键词，而不是纯名称搜索 | 这才是商务组每天的工作 |
| P1 | 确认时强制：至少一份证明文件 **或** 不少于 20 字的核验说明 | 出问题能追溯 |
| P2 | “拟派项目团队”对象：岗位、人员、证书、社保单位，导出人员表 | 技术标也要引用同一批人 |
| P2 | 联合体/分包协议作为一等原件类型，未上传则正式导出保持草稿 | 常见废标点 |

## 4. 路径三：技术标长文写作

### 4.1 当前方法

流水线（组互斥任务）：导入 → 标段 → 招标分析 → 目录（可走 outline v2 / 已有方案扩写）→ 全局事实 → 正文。

正文生成（`content-generation.ts` + helpers，合计约 4000+ 行）的质量控制旋钮：

- 默认章节字数指导 **3000**；最多 3 轮扩写，每轮 6 步，目标达到目录规模的 80%；单节扩写增量至少 800 字。  
- 前 3 节做早期内容探针。  
- 默认开启一致性审核；修复模式可走普通或 Agent；最多 2 次。  
- 已有方案扩写可开“原方案覆盖审计”，最多 2 次修补。  
- 配图规划（AI / Mermaid / HTML）在独立队列，生成图写入项目并嵌入 `yibiao-illustration` 区。  
- 已确认商务引用区不可在正文里改权威字段。  
- 主体替换（招标人/项目名等）有专门工具，避免全文误替换。

### 4.2 评价

**作为写作引擎：完整。作为投标技术标：方向偏了。**

技术标得分结构几乎总是：

> 评分点（有分值）← 采购需求条款（有编号）← 响应方式（完全响应 / 正偏离 / 负偏离）← 证明（方案段落、图表、检测报告、类似业绩）。

当前管线是：

> 招标长文 → 18 个摘要槽 → 再生成一套目录 → 再按目录把每节写成约 3000 字 → 事后用模型检查“是否自相矛盾 / 是否覆盖旧方案”。

这解决的是“篇幅和通顺”，不是“条款对条款”。后果在实务里非常典型：

1. **字数目标会鼓励套话。** 3000 字/节 × 数十叶节点，动辄十余万字。评委按评分点抽查，看不到“对本条的响应句”，只看到项目背景、承诺、质量管理体系循环论证。扩写增量下限 800 字会把已经说完的节继续注水。  
2. **一致性审核是模型审模型，不是审招标。** 自相矛盾能抓一些（工期 90 天 vs 120 天），但抓不住“招标要求等保三级、正文写了等保二级”。缺的是**条款级响应矩阵**。  
3. **全局事实一旦写错会污染全书。** 事实来自招标分析（可能未人工确认）+ 知识库 + 已确认商务快照。后一项可靠；前两项不可靠。  
4. **已有方案扩写的覆盖审计默认关闭。** 扩写场景本应默认打开，否则“用旧方案套新招标”是串标/答非所问的高发路径。  
5. **暗标未建模。** 正文、页眉、页脚、图题、业绩名称都可能暴露投标人。系统能做主体替换，但不能做“暗标模式：禁止出现本公司/人员/电话/特定业绩名”。  
6. **配图有规划无投标图则。** 评委需要的是网络拓扑、实施横道图、人员组织、应急流程；Mermaid/HTML 能画，但不绑定评分点，也不保证导出后在 Word 里可读（字体、黑白打印、图号连续）。  
7. **暂停/续写、引用锁定、主体替换** 是编辑器层面的正确能力，应保留。

### 4.3 改进建议

| 优先级 | 建议 | 理由 |
| --- | --- | --- |
| P0 实务 | 在目录生成之后、正文之前，强制产出**技术响应矩阵**：条款号、招标原文、建议响应、拟写入章节、证据快照。未确认矩阵不得开写 | 这是技术标的真正目录 |
| P0 实务 | 默认字数指导改为“按评分点篇幅”或 800～1200 字/叶；去掉 800 字强制增量；扩写改为“覆盖缺口”而非“凑字” | 反套话 |
| P1 | 一致性审核的输入必须包含采购需求原文和评分点，输出“未响应条款清单”，并阻止正式导出 | 模型审模型不够 |
| P1 | 全局事实分来源：`confirmed-snapshot` / `tender-located` / `model-inferred`；仅前两类默认注入正文 | 切断错误放大 |
| P1 | 扩写模式默认打开原方案覆盖审计 | 旧方案套新标是高风险 |
| P1 | 暗标模式：导出前扫描本公司名、人员、电话、地址、特定业绩名 | 暗标废标无法补救 |
| P2 | 配图与矩阵行绑定，导出统一图号、题注、黑白可辨 | 评委按图找方案 |
| P2 | 页数/字数上限按招标“响应文件要求”项回写，超限预警 | 很多招标限页 |

## 5. 路径四：系统编制投标文件的审核

### 5.1 当前方法

三套独立审核工具，外加导出：

1. **响应/偏离表**：从招标结构里用标题正则找“技术/商务偏离表”模板和“采购需求/技术规范”源章；抽取条款行；歧义交给 Pi Agent 按 schema 分类；人工确认后才能正式导出；来源 hash/标段/提取版本变化则 stale（R05）。  
2. **查重**：招标 vs 投标文件的目录结构、标题 bigram、正文、元数据、图片哈希；解析走有界 worker 与文档解析共享槽位（R08）。风险阈值 0.75/0.55/0.35。  
3. **废标/无效项**：单次聊天整理四段 Markdown；与招标分析里的 `discardedBids` 槽部分重叠。  
4. **技术标 Word**：大纲 → docx，含 Mermaid/图片；**没有**与偏离表确认、废标项、商务正式版绑定的总闸。商务 ZIP 有总闸。

### 5.2 评价

**单点工具有专业度，缺少“出厂检查单”。**

- 偏离表走“先找招标自己的表，再抽源章”，比凭空生成偏离表正确；stale 校验避免用过期招标出表。标题正则无法覆盖各地千奇百怪的表名（“技术规格偏离对照表”“星号条款响应表”“★项一览”）。  
- 查重对**防止本公司新旧方案大面积复制**有用，对评委关心的“与其他投标人雷同/招标文件原文大段粘贴”帮助有限——系统没有跨项目语料，也不区分“允许的招标原文引用”和“抄招标当响应”。  
- 废标项抽出来之后，**不阻断技术标导出**。投标现场最痛的是：废标项写在检查页里，正本却没改。  
- 技术标 Word 导出不检查：偏离表是否已确认、是否还有负偏离未说明、商务正式版是否 ready、暗标是否露名、引用锁是否完整。商务路径已经证明这种总闸可以做。

### 5.3 改进建议

把三套工具收成一份 **《投标文件出厂检查单》**，正式导出（技术 Word + 商务 ZIP）共用：

| 检查项 | 不通过时 |
| --- | --- |
| 标段已人工确认 | 禁止分析/写作/导出 |
| 招标分析必填项均已人工确认或标为不适用 | 禁止开写正文、禁止正式导出 |
| 商务要求全部 `humanEdited`，正式版无 pending/unknown 关键项 | 仅允许缺项草稿 |
| 偏离表已确认且来源未 stale；负偏离均有说明 | 禁止正式导出 |
| 废标/无效项每条有“已响应/不涉及+理由” | 禁止正式导出 |
| 暗标模式扫描通过（如启用） | 禁止正式导出 |
| 已确认引用锁完整 | 禁止正式导出 |
| 查重高风险组有人工结论 | 警告或禁止（策略可配） |

偏离表：在正则之外，允许用户**框选源章和模板表**；Agent 分类只做建议。  
查重：增加“大段招标原文未改写”检测（这是评委能一眼看出的敷衍）。  
废标项与招标分析 `discardedBids` 合并为同一对象，避免两套清单打架。

## 6. 横切问题（投标人会问、系统要能回答）

| 问题 | 现状 | 建议口径 |
| --- | --- | --- |
| 能否直接拿去投标？ | 不能。真实样本与模型未验收；技术标无出厂总闸 | 对外只称“辅助编制”，输出必须经项目经理签发 |
| 暗标怎么办？ | 无模式 | 未做暗标扫描前，暗标项目不要用本系统出正本 |
| 联合体/分包？ | 无一等对象 | 未上传协议则商务正式导出保持草稿 |
| 报价？ | 明确不做，正确 | 界面避免“投标计算器”残留误导 |
| 电子标（CA、加密包）？ | 不做 | 只出 Word/ZIP，由平台客户端封装 |
| 多标段多本？ | 有标段切分，导出仍偏“一个项目一本” | 按标段独立工作区 + 独立出厂检查 |
| 模型胡编条款？ | 商务有原文定位；技术 18 项和正文没有同等门禁 | 技术侧对齐商务门禁 |
| 图片/扫描件？ | 有 MinerU 回落，真实质量未知 | 扫描件未确认 OCR 质量前，表格类资格条件改为人工录入 |

## 7. 建议实施顺序（按投标风险，不按工程难度）

**第一批（不补就不能当“编制系统”用）**

1. 标段人工确认门禁。  
2. 招标分析项原文定位 + 未确认不得注入事实/正文。  
3. 技术响应矩阵（条款 → 章节 → 证据），确认前不开写。  
4. 出厂检查单总闸（技术 Word 与商务 ZIP 共用）。  
5. 废标项闭环到导出。

**第二批（明显减废标/失分）**

6. 资格条件 `allOf/anyOf` 与候选门槛过滤。  
7. 确认时的证明页或核验说明。  
8. 暗标扫描。  
9. 字数策略从“凑 3000”改为“覆盖缺口”。  
10. 偏离表支持人工框选源章。

**第三批（质量迭代，依赖真实样本）**

11. 3～5 份脱敏招标对照集（解析、18 项、商务抽取、偏离表、废标项）。  
12. 表格对象化。  
13. 拟派团队对象。  
14. 配图与矩阵绑定、图号题注。  
15. 真实 MinerU/模型验收（现有 STATUS 门禁，不能用合成数据关闭）。

**明确不要做的**

- 不要做自动评分/中标预测。  
- 不要自动把 `unknown` 改成 `met`。  
- 不要为了“写得长”继续加大扩写轮次。  
- 不要在未确认招标解析质量前，把 MinerU 回落标成成功。  
- 不要把电子标平台封装、报价、CA 签章塞进本迭代——会稀释组卷纪律。

## 8. 与现有工程状态的关系

- 本审查**不修改** [STATUS](STATUS.md) 的 DONE/BLOCKED。P1/P3 因真实服务与样本 BLOCKED 的项，仍然是产品能力的上限。  
- 2026-09-13 的 R01–R12 修复（处理出口、导入 staging、取消、查重隔离、偏离表 stale 等）对投标纪律是加分项，尤其是“失败不覆盖原件/成功版本”。  
- 商务路径已经实现的“原文定位、人工确认、快照复制、正式/草稿分流”，应视为技术标和审核路径的**内部设计规范**，而不是商务模块的特例。
- 将本审查与 [AI-BID-OS-WRITING-LESSONS-2026-09-14](AI-BID-OS-WRITING-LESSONS-2026-09-14.md) 收成改造初步方案见 [AI-BID-OS-TRANSFORMATION-PLAN-2026-09-14](AI-BID-OS-TRANSFORMATION-PLAN-2026-09-14.md)。

## 9. 结论

| 路径 | 工程完成度 | 投标可用度 | 一句话 |
| --- | --- | --- | --- |
| 招标解析 | 高（原件、版本、隔离、回落） | 中偏低 | 骨架对，表格/标段/抽取复核不够 |
| 商务组卷 | 高 | 中高（人工确认后） | 最接近开标纪律，检索和资格逻辑还弱 |
| 技术长文 | 高（流水线完整） | 中偏低 | 能写长，不能保证条款对条款 |
| 编制审核 | 中高（三套工具） | 中 | 有零件，无出厂总闸 |

**若只做五件事：标段确认、分析项原文定位、技术响应矩阵、出厂检查单、废标闭环。** 做完这五件，系统才从“AI 写标书”变成“按招标文件编制并挡住常见废标”。其余优化（表格对象、暗标、联合体、对照集）在真实样本进门后迭代。
